> Источник: письмо с заданием + файл проекта `*.plcopen.xml` (Astra.IDE / Codesys 3.5, формат PLCopen).
> Цель этого файла — не терять детали ТЗ во время разработки, не листая письмо туда-сюда.

## 1. Ответы заказчика на уточняющие вопросы (получены, зафиксированы)

1. **Порядок строк** — не сортировать, оставить как в исходном XML (естественный порядок обхода). ✅ Подтверждено.
2. **Совпадение имён GVL** — невозможно в принципе: Codesys не допускает создание двух GVL с одинаковым именем внутри одного ПЛК. Если такое всё же встретится в файле — это **ошибка исходных данных**, не штатная ситуация. В присланном `KA107__GPA2.plcopen.xml` такой ошибки нет.
   → Отдельную валидацию на дублирование имён GVL стоит добавить как **проверку целостности данных** (см. раздел 6, обработка ошибок), а не как штатную ветку логики путей.
3. **Битый `export`-JSON5** — переменная **не пропускается молча**. В GUI должна быть область «журнал выполнения задачи ПО» (лог), куда выводится **предупреждение (severity Warning)** по шаблону:
   ```
   {nameGVL}.{nameVar}: Ошибка парсинга JSON атрибута "export": {текст ошибки, если имеется}
   ```
   Сама переменная при этом в CSV не попадает (т.к. невозможно проверить условие `communication.cycle == fast`), но факт ошибки логируется, а не проглатывается тихо.
4. **Стек/язык** — на усмотрение исполнителя ("на чём удобно"). Пожелание заказчика — Flutter/Dart (весь стек на одном языке), но это не требование, а предпочтение. Финальное решение — моё.

**Регистронезависимость `symbol != "none"`** — вопрос не задавался, ответа нет. Оставляю рабочее допущение: сравнение регистрозависимое (точное), пока не всплывёт проблема на реальных данных.

## 2. Карта XPath (откуда что брать)

| # | Сущность | XPath | Источник значения |
|---|---|---|---|
| 1 | ПЛК | `/project/instances/configurations/configuration[position()>0]` | атрибут `name` узла |
| 2 | GVL-блок (Global Variables List) | `//configuration/resource/globalVars[position()>0]` | атрибут `name` узла |
| 3 | Переменная | `//globalVars/variable[position()>0]` | атрибут `name` узла |
| 4 | Тип переменной | `//variable/type/*` | атрибут `name`, **если** тег узла = `derived`; **иначе** — имя самого тега узла |
| 5 | Атрибут (аннотация) | `//addData/data/Attributes/Attribute[position()>0]` | `Name` (имя атрибута) + `Value` (значение атрибута) — атрибуты самого узла |
| 6 | Исходник GVL в виде ST-кода | `//globalVars/addData/data/InterfaceAsPlainText/xhtml` | текстовое содержимое, с Codesys-расширениями в `{...}` (справочно, для отбора не обязателен — вся нужная инфа уже есть в Attribute-узлах п.5) |

**Иерархия узлов** (для понимания вложенности при обходе):

```
configuration (ПЛК, name)
 └─ resource
     └─ globalVars (GVL-блок, name)
         ├─ addData/data/Attributes/Attribute*   ← атрибуты уровня GVL
         ├─ addData/data/InterfaceAsPlainText/xhtml   ← ST-текст (справочно)
         └─ variable* (переменная, name)
             ├─ type/*                            ← тип переменной
             └─ addData/data/Attributes/Attribute* ← атрибуты уровня переменной
```

## 3. Формат `export` — customJSON5

Значение атрибута `Value` у `Attribute[@Name="export"]` — это НЕ чистый JSON. Формат:

| Стандартный JSON | Как записано в `export` |
|---|---|
| `"` (кавычка) | XML-entity `&quot;` (и т.п. XML-экранирование) |
| `{ }` (словарь) | `( )` — круглые скобки |
| `{ }` внутри строкового значения | остаются как есть, не трогать |
| висячая запятая в конце списка/словаря | допустима (JSON5-расширение) |
| ключ без кавычек | допустим, если не содержит спецсимволов (JSON5-расширение) |

**Мини-парсер (шаги обработки строки `export`):**
1. Найти текст атрибута `export`.
2. Раскодировать XML-entities (`&quot;` → `"`, `&lt;` → `<`, `&gt;` → `>`, `&amp;` → `&`).
3. Заменить `(` → `{` и `)` → `}` (скобки внутри JSON-строк — т.е. между кавычками — не трогать!).
4. Скормить результат JSON5-совместимому парсеру (или, если библиотеки нет — доработать под висячие запятые/ключи без кавычек вручную) либо распарсить целевые поля (`communication.cycle`, `name.full`, `name`) точечно без полного JSON5-парсера.

⚠️ Важный нюанс шага 3: строковое значение внутри JSON тоже может содержать `(` / `)` — их **менять не надо**. Наивная глобальная замена скобок сломает такие строки. Нужна замена с учётом того, находимся ли мы внутри кавычек (простой конечный автомат по символам, отслеживающий "внутри строки / вне строки", с учётом экранирования `\"`).

## 4. Условия отбора «быстрого технологического параметра»

Переменная попадает в выгрузку, если **одновременно**:

1. **Объявлена внутри GVL-блока** конкретного ПЛК (сам факт того, что мы её нашли по XPath из п.2 таблицы выше — уже гарантирует это условие).
2. **`symbol`-атрибут ≠ "none":**
   - если у **переменной** есть `Attribute[@Name="symbol"]` → берём его `Value`, сравниваем с `"none"`;
   - если у переменной такого атрибута **нет** → ищем `Attribute[@Name="symbol"]` у **родительского GVL-блока**;
   - в обоих случаях значение атрибута не должно равняться `"none"` (регистрозависимо — см. допущение в разделе 1).
3. **`export`-атрибут задан и парсится**, и внутри распарсенного JSON5-объекта путь `$.communication.cycle` существует и равен `"fast"` **без учёта регистра** (`"Fast"`, `"FAST"` — тоже подходят).

Если хотя бы одно условие не выполняется (включая случай "атрибут `export` отсутствует вовсе", "путь `communication.cycle` отсутствует в JSON", "значение не равно fast") — переменная в выгрузку не идёт.

## 5. Формат результата — CSV на каждый ПЛК

- Один CSV-файл на каждый узел `configuration` (ПЛК) из проекта.
- Имя файла должно содержать имя ПЛК.
- Заголовки столбцов (ровно так, порядок важен):

| № | Столбец | Содержимое |
|---|---|---|
| 1 | Номер | Порядковый номер строки, инкремент с 1 (или с 0? — не оговорено явно, по умолчанию с 1) |
| 2 | Путь | `"{nameGVL}.{nameVar}"` |
| 3 | Тип | Тип переменной (см. п.4 карты XPath) |
| 4 | Имя | Цепочка fallback: `$.name.full` (из JSON объекта `export`) → если нет → `$.name` (из того же объекта) → если нет → `"---"` |

## 5.1. Наблюдение по реальным данным (KA107__GPA2.plcopen.xml)

Атрибут `export` в реальном проекте используется не только под customJSON5 —
встречаются как минимум два других, полностью независимых мини-формата
в значении того же атрибута `export`:

- `an:[GVL.mde_hmi] af:[.number]` — похоже на адресацию для протокола IEC104
  (GVL с именем `IEC104`);
- `a n:[Имя] u:[Единица] d:[Точность] lolim:[Мин] hilim:[Макс]` — похоже на
  описание настроечного параметра (замечено в GVL `s_tunpar`, `acpar`).

**Это не баг парсера и не повод его "чинить"** — такие значения формально
не являются customJSON5, поэтому условие 3 (раздел 4) для таких переменных
не выполняется, и они закономерно не попадают в выгрузку. Обработка не
требует спецкейсов: `Json5ParseError` из `json5_parser.py` перехватывается
в `core/fast_param_finder.py` единым образом и превращается в
Warning-запись в журнале (см. раздел 1, ответ заказчика №3).

На реальном файле: из 648 переменных с атрибутом `export` — 609 успешно
парсятся как customJSON5, 39 — нет (относятся к двум другим форматам выше).
Из 609 успешно распарсенных — 14 удовлетворяют условию `communication.cycle
== fast` (регистронезависимо).

## 6. Требования к приложению (эргономика)

1. Минимум зависимостей на целевой машине; если рантайм/либы нужны — явно перечислить версии.
2. Минимальный размер скомпилированного бинарника (если не чистый интерпретируемый скрипт).
3. GUI:
   - диалог выбора файла проекта (`.xml`);
   - диалог выбора каталога для результатов;
   - кнопка запуска основного алгоритма.
4. Сообщение об успешном завершении (диалог или область в GUI).
5. Сообщение об ошибке при некорректных входных данных — максимально подробное (какой узел/атрибут/файл вызвал проблему).
6. **Область «Журнал выполнения задачи ПО»** в GUI — обязательна (ответ заказчика, п.3 раздела 1). Минимум — вывод предупреждений (Warning) по битому `export`-JSON с шаблоном `{nameGVL}.{nameVar}: Ошибка парсинга JSON атрибута "export": {текст ошибки}`. По аналогии можно логировать и другие некритичные аномалии (например, обнаруженное дублирование имён GVL — как severity Error/Warning, раз это признак битых исходных данных).

## 7. Общий алгоритм (высокоуровнево, без кода)

```
1. Загрузить и распарсить XML-файл проекта (валидировать, что это вообще похоже на PLCopen).
2. Для каждого configuration (ПЛК):
   a. Для каждого globalVars (GVL-блок) внутри configuration:
      - извлечь GVL-level Attribute[@Name="symbol"], если есть — сохранить как fallback-значение.
      - для каждой variable внутри globalVars:
          - извлечь имя переменной, тип переменной (п.4 карты XPath).
          - извлечь variable-level Attribute[@Name="symbol"] (или fallback от GVL).
          - извлечь variable-level Attribute[@Name="export"], распарсить как customJSON5.
          - проверить 3 условия отбора (раздел 4).
          - если подходит — сформировать строку (Номер, Путь, Тип, Имя) с учётом fallback для «Имя».
   b. Записать список подходящих переменных этого ПЛК в CSV-файл, имя которого включает имя ПЛК.
3. Показать пользователю сообщение об успехе / ошибке.
```
